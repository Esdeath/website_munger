# Playbook:从知识库批量生成「逐字可考」的文章(并行 agent 流水线)

**类型**:通用方法论(corpus-agnostic),不限于本仓库的芒格项目
**适用场景**:有一个**固定的知识库 / 语料库**,要从中批量生成若干篇文章,且每篇都必须**逐字引用来源、可被机器核验、不得杜撰或张冠李戴**。
**本仓库的具体实例**:`articles/`(芒格关键词长文),语料在 `shareholders/` + `speech/`,校验脚本 `tools/check_article.py`,模板 `articles/_TEMPLATE.md`,项目状态/待办池 `articles/TODO.md`。下文用「{占位符}」表示需按项目替换的部分。

> 这套流水线在本仓库连续跑了 12 批、46 篇文章,以下是被验证有效的做法、踩过的坑,以及**如何把 token 成本压到最低**。

> **两类读者**:
> - **要给同一个知识库再生成一批文章** → 直接看 §1–§7(编排、门槛、省 token、prompt 骨架、控制器清单)。
> - **要用一套全新资料从零搭一个同类知识库** → 先看 **§0 从零搭建路线图**,它把下面的所有部件按正确顺序串成一次冷启动。

---

## 0. 从零搭建路线图(换一套新资料时,一步一步)

下面把整条流水线「冷启动」一次。**最关键的认识**:本方法论详细讲了「怎么由关键词生成文章」,但一个新知识库**真正的第一步是「关键词从哪来」和「合同(校验器)怎么定」**——这两步没做好,后面再快也白搭。

### 阶段 0 · 备料(最容易被忽视、却决定成败)
1. **切分来源**:把原始资料拆成「一个文件 = 一个独立来源」。**文件名要带可引用信息**(年份 / 标题 / 作者),因为文章的引用出处通常直接取自文件名。
2. **统一编码与标点**:先决定并批量归一化——全角还是半角标点、弯引号还是直引号、是否保留 `**` 加粗。**这一步偷懒,后面必踩「半角标点坑」**(见 §4.2),会让逐字校验整篇 FAIL。
3. **放进固定目录**(如 `corpus/` 或本项目的 `shareholders/` + `speech/`)。

### 阶段 1 · 提取关键词(新知识库的真正起点)
4. **定分类体系**:先有几个大类(本项目是 8 类:投资原则 / 思维方法 / 人性偏误 / 品格处世 / 常引用人物 / 公司案例 / 学科体系 / 宏观警示)。分类让选题不重不漏。
5. **挖候选词**,两条路任选/并用:
   - (a) **统计法**:对一批候选词跑 grep,数 **覆盖**(出现在几个文件)+ **频次**(总命中)。适合你已经大致知道有哪些主题。
   - (b) **agent 抽取法**:派若干 agent 各读一部分语料、各自吐主题词,再汇总去重。适合资料非结构化、你还不知道有哪些主题。
6. **过门槛 + 去重**:把覆盖太低(凑不满「≥N 引用 / ≥M 来源」硬门槛)的词砍掉;把高度重叠的合并或给差异化角度。
7. **产出待办池**(本项目的 `articles/TODO.md`):每个关键词记 覆盖 / 频次 / 分类 / 勾选框。这就是后续每批的「选题面板」。

### 阶段 2 · 立合同(linchpin,务必先于量产)
8. **写校验器**(本项目 `tools/check_article.py`):逐字存在性 + 引用数下限 + 来源数下限 + 必备小节 + frontmatter 完整。**它把「合格」变成可自动判定的 PASS/FAIL,写手才能自助收敛到过为止**(§2)。没有它,整条流水线无法无人值守。
9. **写模板**(本项目 `articles/_TEMPLATE.md`):文章小节骨架 + 写作语气清单(放成文末注释,成文前删)。
10. **写一页项目配置**(本项目就是瘦身后的 `TODO.md` 顶部):语料路径、引用出处格式、标点规范、分类、提交约定。**方法论直接复用本 playbook,不要重写**。

### 阶段 3 · 试产 1 篇(别急着上量)
11. 手动跑一遍 写手 → 核查 → PASS,**专门用来打磨校验器和模板**。第一篇必然暴露门槛太松/太严、模板缺节、出处格式不统一。本项目当初也是先做一个试点批再上量。

### 阶段 4 · 批量生成(优化版稳态循环,每批 ~3 篇)
12. 按 §7 控制器清单跑:**控制器预挖 `file:line` 清单 → 并行写手窄读 → 校验器 PASS → 独立核查 → 控制器统一提交**。

### 阶段 5 · 维护
13. 每批更新索引页、进度、把新踩的坑追加进待办池的「选词注意」和项目记忆。

> **一句话内核(换任何资料都不变)**:先定**合同(校验器)+ 分类** → 从语料**提关键词建待办池** → **试产 1 篇**校准 → 然后才是控制器预挖+窄读省 token、写手并行、独立核查兜语义、统一提交的稳态循环。

## 1. 核心编排模式:控制器 + 并行写手 + 独立审查 + 控制器提交

一个主循环(控制器)+ 三类一次性子 agent。**每个子 agent 的上下文是隔离的**——它不继承会话历史,只拿到你为它精心构造的 prompt。这既保证专注,也保护主循环的上下文。

```
控制器(主循环)
 ├─ 选题 + grep 可行性预检(确认能过门槛)
 ├─ 并行派发 N 个【写手 agent】 ── 每人 1 篇,写到各自独立文件,禁止 git
 ├─ 并行派发 N 个【审查 agent】 ── 每篇 1 个独立核查者,只改自己那篇,禁止 git
 ├─ 全量跑校验脚本复验
 ├─ 更新索引/目录
 └─ 提交(控制器统一做)
```

**为什么这样分工**

- **写手并行、各写各文件**:互不依赖,可同时跑。**子 agent 绝不能跑 git**——并行提交会冲突;提交权只在控制器。
- **审查必须独立**:校验脚本只能保证「引文逐字存在」,**保证不了**出处年份对不对、说话人/作者是不是本人、有没有过度引申、数字史实对不对。换一个没写过这篇的 agent 来挑刺,才挑得出来(本仓库就靠它抓到过把 2010 年的话误标成 2007 年)。
- **控制器收口**:复验、更新索引、按约定提交,串起整条流水线。

---

## 2. 机器可核验的「门槛」是整条流水线的合同

整套方法成立的前提:有一个**确定性的校验器**,任何一篇文章必须通过它才算完成。校验器把"质量"变成可自动判定的 PASS/FAIL,写手可以自己反复跑到过为止,无需人盯。**质量优先时,这是最高杠杆的投资点:每把一个检查写进脚本,就等于让所有未来文章免费、永久地受这道保护——不必靠 agent 每篇重做。** 通用的门槛项:

1. **逐字存在性**:每条引用(按省略号切片后)必须逐字出现在语料中 → 杜绝杜撰/错字。
2. **引用量下限**(如 ≥12 处)。
3. **来源多样性下限**(如 ≥4 个不同来源/年份)。
4. **必备结构**(如必须有某几个小节标题)。
5. **元数据完整**(frontmatter 字段齐全;**声明的 quote_count 必须等于实际引用数**——否则 FAIL)。
6. **每条引用必须带出处**(每个 blockquote 组都要以 `——《篇名》年份` 结尾)→ 杜绝"裸引用"。
7.(可选,`--dup`)**跨篇逐字重复检测**:本篇引用若与其他文章逐字撞车则 WARN(默认关闭——短语撞车噪声大;量产前由控制器对新关键词单独跑一次,用来强制差异化角度)。

> 把检查分成 **ERR(硬门槛,FAIL)** 和 **WARN(提示)** 两级。**ERR 只放"几乎不会误报"的检查**(逐字、计数、必备节、quote_count、裸引用);凡是靠模糊字符串匹配、容易误报的(如 sources 列表对账),要么不放进脚本、交给独立核查 agent,要么做成默认关闭的可选项——**一个动辄误报的 WARN 会训练人忽略所有 WARN,反而毁掉质量纪律**。
> 没有这样的校验器就先写一个——它是把"写手能自助收敛"的关键,也是后面所有 token 优化的安全网(允许 agent 大胆产出,门槛兜底)。

## 3. Token 成本:钱花在哪,怎么省

> 实测:一篇"正常"写手 ≈ 85–100k tokens;**高频关键词会失控到 ~200k**(命中文件多、被整篇读进上下文)。审查每篇 ≈ 45–75k。一批 3 篇(写+审)常在 ~400–600k。下面按**性价比从高到低**排列优化手段。

### 成本驱动(按量级)

1. **整篇读大文件、且反复读** —— 第一大头。来源文件动辄几千 token;高频词命中几十处、跨十几个文件,写手往往整篇吞进上下文。
2. **写手和审查重复 grep+读同一批源文件** —— 重复劳动。
3. **失败/死亡 agent 的浪费** —— 子 agent 偶发中途报错(见 §5),已耗的读取打水漂。
4. **校验失败的返工循环** —— 一个编码/格式坑(见 §4.2)能让全部引文 FAIL,然后回源重读重抄。

### 优化手段(高 → 低杠杆)

1. **只读命中窗口,别整篇读(最大杠杆)。** 先 `grep -n` 拿行号,再用带 `offset/limit` 的读取只取命中处前后 ~30 行。2000 行的文件只读 60 行,单篇省一大半。对高频词尤其关键。
2. **限定读取文件数 + 跨层取样。** "≥4 来源"只需 6–8 个好来源,不必把某主题的全部文件读完;按年代/场合分层各取几个即可。
3. **控制器预挖,把候选清单交下去。** 控制器(相对便宜)先跑一遍 grep,把 `文件:行号` 候选清单塞进写手 prompt;写手只读这些窗口、不再从零探索。**同一份清单复用给审查员**,直接消除 §成本2 的重复读取。
4. **审查改成「抽查 + 盯风险点」,不逐条全核。** 抽查 4–5 条关键引用回源核对 + 重点核查写手自报的风险项,而非把每条都重新 grep。本仓库抓年份错误靠的就是针对性核对,抽查足矣。
5. **机械型子任务用便宜模型。** 纯格式/编码修复、轻量核对可用更小的模型(`Agent` 工具支持按调用覆盖 `model`);需要判断的写作保留强模型。
6. **复制而非重打,防返工。** 让写手**直接从读取结果里复制引文**(保留原始字符/标点),不要凭记忆重打——重打正是错字和半角标点混入的源头(见 §4.2)。
7. **早验证、勤验证。** 写完一节就跑一次校验器,早发现早改,别攒到整篇 FAIL 才回源。

> 综合 #1 + #3(窄读 + 预供清单)通常能把写手从 ~100k(高频词 200k)压到 ~40–60k,审查再砍一半。

## 4. 校验器查不出的坑(为什么必须有独立审查 + 编码注意)

### 4.1 语义类(交给独立审查 agent)

- **出处/年份错配**:引文逐字存在,但标错了来源篇目或年份。让审查员**打开被引源文件**核对篇名与年份。
- **说话人/作者错配**:在访谈/合集/问答类来源里,引文可能出自**提问者、第三方、编者导言**而非目标作者本人。务必回到上下文确认。
- **过度引申**:用一条引文去"证明"它其实没说的结论。
- **自造比喻冒充原话**:标题/小标题的意象必须是来源中本人用过的词,否则只能放在编者口吻里、不能伪装成引用。
- **数字/史实/日期/年龄**:只用来源里逐字出现的数字;涉及人物年龄按其出生年核算。

### 4.2 编码 / 归一化坑(通用,极易整篇翻车)

校验器通常只做**部分**文本归一化(如去空白、去引号、去加粗),但**不会**把半角标点 `, . ? ;` 归一成全角 `，。?；`,反之亦然。若语料用全角而写手敲了半角,引文会逐字比对失败、报"未在语料中找到"——即使内容完全正确。

**对策**:确认语料实际使用的标点/字符集;要求写手严格匹配;优先**复制**而非重打。**当一篇文章"几乎所有引文都 FAIL"时,先怀疑这个坑,而不是怀疑内容。**

---

## 5. 失败恢复:子 agent 中途死掉怎么办

子 agent 可能因瞬时错误(如 API 计费/额度报错、超时)中途崩溃、返回空结果。但它**通常已经把半成品文件写到了磁盘上**。

**对策**:不要从零重写。先检查磁盘上有没有半成品 → 跑一遍校验器看缺什么 → 派一个**聚焦的「修复」agent**(只做缺失的那部分,如修标点、补引用、核对出处)。本仓库一次写手崩在 API 402,留下了内容完整但全是半角标点的文件,一个修复 agent 几十 k token 就救回来了,远比重写便宜。

## 6. 可复用的 prompt 骨架

### 写手 agent(每篇一个,并行)

```
你要为【{项目/合集说明}】写 1 篇文章,主题/关键词是【{关键词}】(分类:{分类})。
工作目录 {repo}。只产出 1 个新文件,禁止任何 git 命令,不要改其他文件。

【硬门槛】文件必须通过 `{校验命令}` 打印 PASS、exit 0:
- 每条引用逐字出现在语料 {语料目录};按省略号切片核验;{≥N 处引用};{≥M 个来源}。
- 必备小节 {…};frontmatter 字段 {…};声明计数=实际计数。
- 编码注意:{语料用全角标点},写手须严格匹配,**直接从读取结果复制引文,勿重打**。

【流程】
1. 采集:先 `grep -n` 拿行号,再**只读命中处前后 ~30 行**(offset/limit),不要整篇读;
   最多取 {6–8} 个来源,跨年代/场合取样。{可在此粘贴控制器预挖的候选 file:line 清单}
2. 核对说话人/作者是本人(排除提问者/第三方/编者导言)。
3. 套模板 {模板路径} 成文;解读用第三人称编者口吻,不冒充原作者;引文 blockquote + `——《篇名》年份`。
4. 写完即验证,反复跑到 PASS;副标题比喻须有据。
【返回】文件路径;最终 引用数/来源数/PASS;所引来源;副标题依据;留给审查员复核的判断点与风险。不要提交。
```

### 审查 agent(每篇一个,独立)

```
你是【{文件}】的独立事实核查者。校验脚本已保证逐字存在,你专查它查不出的:
出处/年份错配、说话人/作者错配、过度引申、自造比喻冒充原话、数字/史实/年龄错误。
{粘贴写手自报的风险点,优先核查}

【做法】抽查 4–5 条关键引用 + 全部风险点:grep 定位→打开源文件→核对篇名/年份/说话人/上下文。
发现问题**直接在这一个文件里改**(禁 git、不碰其他文件),改完重跑 `{校验命令}` 确保仍 PASS。
注意编码:引文保持 {全角标点}。
【返回】问题清单(分严重度)+ 改动前后 + 最终校验结果 + 有意保留项及原因。已干净则明说。
```

## 7. 控制器运行清单

1. **选题**:从待办池按"覆盖广 + 频次高 + 与已写不重叠"挑;尽量跨不同分类。
2. **可行性预检(立项前必做)**:`grep` 统计候选词的命中文件数/次数,确认能过 {≥引用 / ≥来源} 门槛;低覆盖词容易 FAIL,先验证再立项。
3.(可选,省 token)**预挖候选清单**:控制器跑一遍 grep,把 `file:line` 清单分别塞进写手 prompt。
4. **并行派发写手**(一条消息内多个 Agent 调用,真并行)。
5. **回收 + 检查磁盘**:有无半成品?死掉的 agent 走 §5 修复路径。
6. **并行派发独立审查**,每篇带上该写手自报的风险点。
7. **全量复验**:对所有文章跑校验器(注意把非文章文件如 README/TODO 排除)。
8. **更新索引/目录**:计数、新增条目、待办勾选。
9. **提交**:每篇一个 `{commit 约定}`,最后一个索引提交。按项目约定决定直接提交主干还是开分支/PR。
10.(可选)**沉淀**:把本批新踩的坑写进项目记忆/本文档。

## 8. 迁移到新项目时,替换这几样

| 部件 | 本仓库实例 | 换新项目时替换为 |
|---|---|---|
| 语料库位置 | `shareholders/` + `speech/` | {你的知识库目录} |
| 校验器 | `tools/check_article.py`(逐字+计数+结构) | {你的 PASS 门槛脚本} |
| 文章模板 | `articles/_TEMPLATE.md`(8 小节) | {你的结构骨架} |
| 选题来源/分类 | `articles/TODO.md` 待办池 | {你的主题清单} |
| 提交约定 | 每篇 `article: 关键词` + 索引提交,直推 main | {你的 git 约定} |
| 编码注意 | 语料全角中文标点 | {你的字符/标点规范} |

不变的内核:**确定性门槛 + 控制器/写手/审查三分工 + 窄读省 token + 独立审查兜语义 + 失败走修复而非重写。**
